# Deprecation Notices

One file per deprecation that Quark has written by hand. A `// Deprecated:`
marker in the source says *stop using this*; the notice here says *what to use
instead, when the symbol goes away, and what breaks if you ignore it*. Neither
half is enough on its own, so the suite requires both.

## Naming

- `DEP-YYYY-NNN-<slug>.md`, numbered in Quark's own namespace from
  `DEP-2026-001`. The sibling products number independently, so
  `DEP-2026-001` here and `DEP-2026-001` in Nucleus are unrelated.
- One notice per deprecation, not per symbol. A single decision that
  deprecates a type and three functions is one notice covering four surfaces
  — see [`DEP-2026-002`](DEP-2026-002-listener-registration-contract.md).

## The format the guard enforces

The suite runs a check over the three products that reads every hand-written
`// Deprecated:` paragraph, joined across line breaks, and requires all of:

1. the paragraph starts with `Deprecated: ` — the Go convention, which is what
   `go doc`, editors and staticcheck's SA1019 read;
2. it names the replacement;
3. it contains the sentence
   `Scheduled for removal in vX.Y.Z, no earlier than YYYY-MM-DD.`;
4. that version is greater than the version the suite manifest pins for Quark
   — a promise naming a version already published is a contradiction, and it
   fails;
5. it cites a `DEP-YYYY-NNN` id, and the matching file exists in this
   directory.

Generated code is out of scope by construction: markers under a
`Code generated ... DO NOT EDIT.` header are written by the generator, and
rewriting them would be lost on the next run.

## Behaviour changes

A behaviour that changes at the major with no symbol going away gets a notice
here too, with `Scope: behaviour` and an "Earliest change" line in place of
"Earliest removal". There is no `// Deprecated:` marker to carry it — the
method stays — so the guard above has nothing to read; the notice and the
godoc of the affected method are the announcement, and the tests that pin the
v1 behaviour are named in the notice so the change at the major is a diff to
them. See [`DEP-2026-003`](DEP-2026-003-updatebatch-version-check-default.md),
and `DEP-2026-004` to `DEP-2026-010`, the behaviour changes of the 2.0 list
the owner decided on 2026-10-06 and 2026-10-16; each names the test that
pins v1, the exit that exists in 1.x and the date its window opens.

## Removal rules

- **Removals are major-only.** A stable surface is not removed in `v1.x`; that
  is the promise the README makes, and it is why every open notice here names
  `v2.0.0` as its removal version. A Quark major also moves the rest of the
  suite, so the removal date and the removal release are two different
  questions.
- **A minimum of 90 calendar days of notice.** The date in the marker is when
  the deprecation becomes *eligible* for removal, not when it is removed. Both
  numbers are stated in the notice rather than in the code comment, so the
  reasoning has one home.

## What Quark does not have

The sibling register in Nucleus pairs each notice with a migration-assistant
specification and a changelog entry. Quark has neither home:

- there is no `docs/migration_assistants/` tree, and inventing an empty one to
  satisfy a template would not help a reader. The migration guidance lives
  inside each notice's **Migration path** and **Detection** sections instead,
  detailed enough to act on;
- `CHANGELOG.md` is generated by release-please from conventional commits and
  has no `Unreleased` section to write into. A documentation-only change does
  not cut a release, so a deprecation that is announced without a code change
  is announced here and in the godoc marker.
