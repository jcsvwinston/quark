## Notes

- **int / int64** — Go's `int` is 64-bit on every supported platform.
- **uint64** — Stored signed; values above 2⁶³−1 do not fit.
- **float64 with precision=18,scale=4** — Use this for money: binary floats cannot represent every decimal.
- **time.Duration** — Stored as an integer count of nanoseconds.
- **integer primary key** — Auto-increment.
- **string primary key** — For UUID/ULID keys the caller supplies.
- **[]string, []int64, map[string]any** — Serialised as text; no native array or JSONB column yet.

## Integer width

Integers map by the width of the Go type. They used to collapse onto a
single `INTEGER`, which is four bytes on PostgreSQL, MySQL and SQL
Server: an `int64` past 2³¹ was rejected by those engines while
looking fine on SQLite, whose `INTEGER` is dynamically sized.
Auto-increment keys were narrow for the same reason and ran out at
2,147,483,647 rows.

If you have tables created before this changed, `PlanMigration`
reports the widening as an `ALTER COLUMN`. Applying it is safe —
widening loses no data — but on a large table the engine may rewrite it, so
run it when a rewrite is acceptable rather than at deploy time.

## Floating point

`REAL` is single precision on PostgreSQL: about seven significant
digits, where a `float64` carries fifteen. SQLite's `REAL` is an
8-byte IEEE double and was never affected.

For money, use `precision` and `scale` and get a `DECIMAL`:
no binary float represents every decimal fraction exactly.
